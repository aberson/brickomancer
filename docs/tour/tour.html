Brickomancer · a guided tour of one local tool

A photo in, a LEGO instruction booklet out

Five stops, about eight minutes. Brickomancer turns a photo of an object into three LEGO build suggestions and a printable step-by-step booklet. The part worth your time is not the output — it is the rebuild it went through once the first version turned out to be guessing at depth instead of measuring it, and the receipts it kept while doing that.

What it makes

Send a photo to /api/generate/from-image, or a sentence to /api/generate/from-text, and you get back exactly three build suggestions — compact, standard and detailed — each with a rendered preview and a parts list. Pick one, send it to /api/generate/instructions, and LPub3D produces a step-by-step PDF in official-manual style. Python 3.12 and FastAPI behind a React 18 wizard; the README calls it a local-first personal tool — no database, each request getting its own tmp/<uuid>/ scratch directory. Two legs of the pipeline do reach outward: the text path and the piece detector each shell out to the Claude CLI on your own subscription.

The photo leg carries a prerequisite a fresh checkout will not have. It needs a CUDA GPU plus a Hunyuan3D-2mini install that is deliberately kept out of the lockfile, and without it /api/generate/from-image returns a clean 503 rather than a wrong answer — the README lists that among its prerequisites. Brickomancer will also identify the pieces in a photo of your brick pile and report them back, but it does not yet build only from what you own. The suggestion service accepts that inventory and does not apply it; that is issue #64, and the README says so up front.

Version one stopped improving, and the post-mortem says exactly why

The first version had an automated improvement loop. It ran 160 rounds and its average score never left the 3.5–5.1 band. Rather than run more rounds, the project stopped and wrote a root-cause document off the primary data — the 160 logged rows and the rendered previews — and found two ceilings active at once. First, the image path invented depth: it built a radial dome height map, tallest at the middle and shortest at the edges, so a star's points, which live at the edges, simply vanished. Second, the loop committed a change whenever the unit tests passed and never re-rendered the result, so a broken instruction-file setting sat at a score of zero for roughly forty consecutive committed rounds, and about thirty commits went into adding, removing and re-adding the same handful of instruction-file settings. The tally below is the outcome column of those 160 rows: 81 of them committed something, and the average still did not move.

OutcomeCount (of 160)What it means
PASS_COMMITTED81tests passed, change kept — without the output ever being re-rendered
SKIPPED_REVERT41tests failed, change rolled back
SKIPPED_JUDGE_FAILED11the scoring step itself failed
SKIPPED_NO_TOKEN10no model credentials available that round
SKIPPED_TIMEOUT9the round ran out of time
SKIPPED_PARSE_ERROR7the model's reply could not be read
PASS_COMMIT_FAILED1tests passed, the commit did not

Both ceilings are named at the file and line where they live, and both became the rebuild's two design rules: recover depth with a real 3D model instead of a heuristic, and make the commit gate re-render rather than just re-run the tests.

The receipt: the star's points survived

Before rewriting anything, the rebuild ran one spike with a kill criterion attached: install a genuine single-image-to-3D model, run it on the same star photo from Stop 1, turn the resulting mesh into a grid of cubes, and print the flattened silhouette as text. If the points did not survive, the rebuild was not worth doing. They survived — and the committed note contains the printed silhouette itself, so you can check the claim in about two seconds without running anything. The same page records the measured mesh (extents 1.992 × 1.776 × 0.238, a genuinely flat plate — the exact inverse of version one's centre-bulged dome), the hardware (a single 8 GB consumer laptop GPU, which the note names as the binding constraint for the spike), the runtime (~103 s), and the candidate that was rejected: TripoSG, abandoned after failing to build on Windows at three escalating layers, each failure written down rather than summarised as "didn't work".

A bug no unit test could see, frozen into a five-line file

While verifying the toolchain, the project hit a defect the test suite could never catch: the single line 0 !LPUB INSERT COVER_PAGE crashes LPub3D 2.4.9, the program that renders the booklet. It was reproduced three separate ways — with bricks in the step, which produced a zero-size PDF; alone before the first step, which crashed hard and wrote a dump file; and in the documented canonical COVER_PAGE FRONT form, which also crashed. Without that line the same toolchain renders cleanly to a multi-page PDF with a parts page. The fix is deliberately boring. The instruction-file header was frozen to exactly five lines with no cover page, that frozen header was checked in as a fixture, a test guards it, and the improvement loop is forbidden from editing it — it lives in a CONSTRAINTS_TO_PRESERVE list the judge cannot touch. The whole fixture is 101 bytes:

0 Brickomancer Build 0 Name: lpub3d_meta_header.ldr 0 Author: Brickomancer 0 STEP 0 !LPUB INSERT BOM

regression guard in place tests/fixtures/lpub3d_meta_header.ldr, verbatim

This is the class of bug that motivated the rebuild's central rule: a gate that only runs unit tests cannot see a broken render. If you want to run the project's own fast gate, that is one command — it is the command the 285 figure at the top of this page comes from.

It grades itself — and says out loud that the loop does not work yet

The rebuilt improvement loop does what version one did not: apply a change, run the tests, then re-render and re-score, and commit only if nothing got worse — otherwise revert. Then it was run for real, three rounds, and the honest result is that it improved nothing. There is exactly one scored point: the starting baseline, average 8.25, with build stability at 3.0 out of 10, which is real headroom. Rounds one and three died at the step that writes the code change; round two stopped on the reviewer's own list of blocking issues. Zero commits. Zero source files changed.

The write-up pins the cause precisely rather than hand-waving at it: the code-writing step asks the model to return an entire ~1000-line source file as one JSON string, which it never returns cleanly. Seven weeks later an addendum was added to that same file, and it corrects two of the document's own claims.
